# Release Process

This document describes how Karoowa releases are produced, signed, and
published. It is the source of truth — the GitHub Actions workflows in
`.github/workflows/` implement what is written here.

## Cadence

Karoowa is pre-1.0. The cadence is **roughly one minor release per major
milestone (M1, M2, …)**, with patch releases as needed. A milestone is
considered "shipped" when:

1. All phases inside it are complete in the dev plan.
2. CI is green on `main`.
3. The release notes draft has been reviewed by at least one maintainer
   listed in `.github/CODEOWNERS`.

Mainline `main` is always shippable. Long-running feature work happens on
feature branches and merges in via PR.

## Versioning

Pre-1.0:

- **MAJOR** stays at `0`.
- **MINOR** increments on every milestone bump (M1 → 0.1, M2 → 0.2, …).
- **PATCH** increments for security fixes and bug-only releases.
- Minor releases may contain breaking changes; the changelog will call them
  out under a `### Breaking` section.

Post-1.0:

- Strict [Semantic Versioning 2.0](https://semver.org/) — the changelog
  promises break only on major versions.

## Triggering a release

1. Bump `[workspace.package].version` in the root `Cargo.toml` and update
   `CHANGELOG.md` with the new section. Move the contents of `[Unreleased]`
   into the new version's section, leaving `[Unreleased]` empty.
2. Open a PR titled `chore(release): vX.Y.Z`. Merge it once green.
3. From `main` on the merged commit, push a signed annotated tag:
   ```sh
   git tag -s vX.Y.Z -m "Karoowa vX.Y.Z"
   git push origin vX.Y.Z
   ```
4. The `release.yml` workflow runs automatically on tags matching `v*.*.*`.

## Artifact matrix

Each release builds the following targets in the `release.yml` matrix:

| OS / arch              | Triple                          | Format   |
| ---------------------- | ------------------------------- | -------- |
| Linux x86_64 (musl)    | `x86_64-unknown-linux-musl`     | tar.gz   |
| Linux aarch64 (musl)   | `aarch64-unknown-linux-musl`    | tar.gz   |
| Linux x86_64 (gnu)     | `x86_64-unknown-linux-gnu`      | tar.gz   |
| macOS x86_64           | `x86_64-apple-darwin`           | tar.gz   |
| macOS aarch64          | `aarch64-apple-darwin`          | tar.gz   |
| Windows x86_64 (msvc)  | `x86_64-pc-windows-msvc`        | zip      |

Plus an `OCI` image pushed to `ghcr.io/mmxxdynamics/karoowa:vX.Y.Z`.

## Signing & provenance

Every artifact published with a release ships with three companions:

1. **SHA-256 checksums** — `checksums-sha256.txt`.
2. **Sigstore keyless signature** (cosign) — `*.sig` and `*.crt` for each
   archive, plus a signed `checksums-sha256.txt.sig`. Verify with:
   ```sh
   cosign verify-blob \
     --certificate-identity 'https://github.com/mmxxdynamics/karoowa/.github/workflows/release.yml@refs/tags/vX.Y.Z' \
     --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
     --signature checksums-sha256.txt.sig \
     checksums-sha256.txt
   ```
3. **SLSA build-provenance attestation** (Level 3) — verifiable via:
   ```sh
   gh attestation verify karoowa-vX.Y.Z-x86_64-unknown-linux-musl.tar.gz \
     --repo mmxxdynamics/karoowa
   ```

A **CycloneDX SBOM** (`karoowa-vX.Y.Z.cdx.json`) is generated by Syft on the
release runner and attached to the GitHub release.

## Release-notes generation

The release workflow uses `softprops/action-gh-release` with
`generate_release_notes: true` to produce a draft body, then merges in the
`[Unreleased]` section from `CHANGELOG.md`. A maintainer reviews the draft
before clicking **Publish**.

## crates.io

Once the workspace stabilises, public crates (anything under `core/` whose
`Cargo.toml` does not set `publish = false`) will be published from the same
release workflow via [`release-plz`](https://release-plz.dev/). Until then,
`core/` crates are published manually by a maintainer with a verified
crates.io account.

`enterprise/*` crates are **never** published — they all set
`publish = false`.

## Rolling back

If a release is broken:

1. Mark the GitHub release as "draft" or "pre-release".
2. Yank the affected crates on crates.io (`cargo yank`).
3. Open a `chore(release): retract vX.Y.Z` PR that adds a `### Yanked`
   section to the changelog.
4. Cut a fixed `vX.Y.Z+1` patch release.

We deliberately do **not** delete release tags — yank + retract preserves the
history for downstream tools.
